 MQTT 多设备联动系统
 风扇模块(2号板) & 火焰传感器模块(6号板)  —— Readme
==========================================================

一、项目简介
本程序是"物联网项目实践"课程大作业第 1 组的两块 ESP32 节点固件，
严格遵循《MQTT 通信协议规范 V2.0（第 1 组）》。
两块 ESP32 通过同一台 MQTT 服务器(yunyismart.tech)交换报文：
  · 2 号板 = 继电器(风扇)模块，接收并执行下行控制命令；
  · 6 号板 = 火焰传感器模块，采集并上行上报数据。
网页/App 等平台只与 MQTT 服务器通信，与设备端完全解耦。

三、功能描述
1) 2 号板 风扇模块
   · 接收下行命令，控制风扇开 / 关（PWM：on = 全速，off = 停）；
   · 执行后回复 ack 回执，供平台确认命令已被执行；
   · 上电后向 online 主题发布在线状态（Retain），掉线时由遗嘱消息自动发布离线。

2) 6 号板 火焰传感器模块
   · 每秒采集一次火焰强度（AO，12 位 ADC，0~4095）并上行 dat；
   · 火焰开关量（DO）变化时上行 evt：
       检测到火焰 detected(level 3)  /  火焰消失 clear(level 0)；
   · 火焰持续存在期间每 5 秒重发一次 detected，防止平台漏报；
   · 在线 / 离线状态处理同上。

四、通信协议
1) 主题
   202609_PP2/1/cmd      下行：平台 -> 设备    QoS 1，不保留
   202609_PP2/1/report   上行：设备 -> 平台    QoS 0/1，不保留
   202609_PP2/1/online   上行：设备 -> 平台    QoS 1，保留
   设备只订阅 cmd，不订阅 report，从根本上杜绝自回环。

2) 报文格式（信封 + 载荷，JSON）
   {"ver":"1.0","type":T,"seq":N,"src":S,"dst":D,"body":{...}}
     ver   协议版本，固定 "1.0"
     type  报文类型：cmd / ack / dat / evt / sys
     seq   报文序号，从 1 开始自增；ack 沿用对应命令的 seq
     src   发送方（平台为 "web"；设备为其板号 "2" / "6"）
     dst   目标板号（0 表示广播）
     body  载荷，内部结构由 type 决定

3) 报文示例
   下发命令（开风扇）：
   {"ver":"1.0","type":"cmd","seq":1,"src":"web","dst":2,
    "body":{"device":"fan","action":"set_power","param":{"on":true}}}

   执行回执：
   {"ver":"1.0","type":"ack","seq":1,"src":"2","dst":0,
    "body":{"device":"fan","action":"set_power","result":"ok","param":{"on":true}}}

   火焰强度（每秒一条）：
   {"ver":"1.0","type":"dat","seq":12,"src":"6","dst":0,
    "body":{"device":"flame","samples":[{"key":"intensity","value":3120}]}}

   火焰事件：
   {"ver":"1.0","type":"evt","seq":13,"src":"6","dst":0,
    "body":{"device":"flame","event":"detected","level":3}}

   在线状态：
   {"ver":"1.0","type":"sys","seq":2,"src":"6","dst":0,
    "body":{"device":"sys","event":"online","uptime":0}}

五、设计思路
1) 端-云-端解耦
   网页/App 与 ESP32 互不直连，双方都只与 MQTT 服务器收发。新增或更换
   设备时，对方无需改动，系统扩展性好、耦合度低。

2) 信封 + 载荷两层结构
   信封字段（ver/type/seq/src/dst）对所有报文完全统一，载荷(body)按报文
   类型决定内部结构。解析时先校验信封、再按 type 进入载荷，逻辑清晰，
   后续要新增设备或数据点也不必改动框架。

3) 上下行主题分离，杜绝自回环
   控制走 cmd、上报走 report，且设备不订阅 report。这样设备永远不会
   收到自己刚发出的上报报文，彻底避免了"收到自己的回执又当命令执行"
   的无限回环问题。

4) seq 序号关联命令与回执
   回执 ack 沿用命令的 seq，平台据此把回执与命令一一对应，可确认每条
   命令是否真正被执行。

5) 遗嘱消息(LWT)实现在线状态
   连接时登记 offline 遗嘱，设备掉线时由服务器自动发布；再配合 Retain，
   平台随时都能读到每块板的最新在线状态，无需轮询。

6) 火焰检测的工程化处理
   软件去抖 50ms 消除抖动误判；事件限流 500ms 防止刷屏；持续检测期间
   每 5s 重发 detected 防止平台漏报；并在 loop 中用时间戳做非阻塞判断，
   保证上报及时、又不影响命令响应。

7) 配置集中，便于移植
   板号、WiFi、MQTT 服务器、主题、引脚等参数集中定义在 main.cpp 顶部，
   更换网络或接线只需修改一处。

六、引脚与配置
   2 号板：风扇 = GPIO14（PWM 输出）
   6 号板：火焰 AO = GPIO33（模拟量输入），
           火焰 DO = GPIO14（数字量输入，低电平表示检测到火焰）
   两块板：WiFi  = SYM1238340 / sym12138
           MQTT  = yunyismart.tech : 1883
   （若实际接线或极性不同，修改对应 main.cpp 顶部的宏/常量即可）

七、烧录与验证要点
   1) 手动进入下载模式：按住 BOOT -> 点一下 EN -> 松开 EN -> 松开 BOOT，
      再点 Upload（终端卡在 Connecting 时可重复一次上述按键序列）。
   2) 串口监视器（115200）观察启动流程：
      连接wifi成功 -> 服务器连接成功 -> 系统就绪。
   3) 用 MQTTX 连接（服务器 yunyismart.tech:1883，用户名/密码留空），
      订阅 202609_PP2/1/#，向 202609_PP2/1/cmd 发布上面的"开风扇"命令，
      即可看到风扇动作，并在订阅区收到对应的 ack 回执；
      火焰板则会每秒上报 intensity、触发时上报 detected / clear。
